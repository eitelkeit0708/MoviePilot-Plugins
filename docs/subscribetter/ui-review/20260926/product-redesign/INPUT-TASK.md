## 1. 不改变的业务范围

- 仍是 MoviePilot V3 插件，不另建外部管理服务，不增加第二套搜片/身份接口。
- 原生新增订阅入口保留；插件负责已经约定的订阅管理。
- 独立质量策略、逐集基线、观察与冷却、计划取代、秒传/普通上传、暂存齐套、发布串行、STRM关联等业务语义不变。
- 保存前后校验、管理员权限、私密存储、幂等、原始回执和未知结果保护不变。
- 下载器数据删除默认关闭；暂停追踪不等于暂停下载，取消交付不等于删除文件。
- 不为简化界面把未知填成零、缺失、成功或失败，不从文件名猜旧计划规格，不把历史入库等同于当前新版完成。
- 全部已确认功能仍在同次完整交付范围。设计原型是确定同一产品的呈现，不是缩水首期/MVP。

## 2. 这次真正要改的内容

不要继续把“每条审计意见加一个控件/一句说明”当设计。保留技术基础，不锁死当前 DOM、CSS、信息排列和操作分解。

### 2.1 页面层级

保留五个业务域与全宽详情的行为，不为改版再增加一级导航。

作品详情：紧凑作品抬头、当前管理状态、详情页签、业务内容。把重复的全局模式说明压缩为持续可见的状态提示；不在每集重复同一规则免责声明。

方案编辑：进入一份方案时使用聚焦编辑空间，显示方案名称、当前步骤/完成状态、当前内容和一套底部操作。此时不得同时把十二组全局设置导航、共享配置维护表单、五步向导和全局保存栏都作为同等主要入口。

仅在需要切换全局设置时返回设置导航。保留退出与未保存更改保护，不靠隐藏功能解决问题。

窄屏不能只是缩窄桌面。标题/返回/操作/页签要重新排列；常态下不应让重复状态说明消耗首屏大部分区域。使用安全区和真实容器尺寸，不以纯 vh 嵌套制造多重主滚动。

### 2.2 视觉规则

- 在 MP 原生主题内设计，用现有主题色、实色内容表面和统一的组件规格。不要新造与宿主无关的品牌视觉。
- 建立有限的排版层级：作品/页面标题、当前版本和阶段、必要说明、技术明细。不要把绝大多数内容做成同样的小灰字和细分隔线。
- 常规桌面正文 14–16 CSS px、次要文字约 12–13 CSS px可作设计起点，不是对当前截图字号的测量。以真实宿主样式、中文内容和缩放复核。
- 简洁不是全局减小字号/边距；先删除重复内容和无效容器，再调密度。
- 普通按钮、主按钮、危险操作、下拉框、checkbox/switch采用同一套尺寸与状态规则；焦点轮廓保留。
- 作品可复用已有海报缩略图以增强辨认；缺图时用紧凑占位，不额外逐行请求媒体服务，不做海报墙。
- 下载进度有可靠已完成/目标字节时可画进度条；秒传重试没有百分比就显示次数和下一次重试；未知外部结果不得画成完成或重新开始。

## 3. 信息表达：先结论，再原因，最后证据

每集常态行只需呈现：集号、最近确认的库内版本、本轮升级版本、当前阶段/进展、下一步。更多内容就地展开。

示意（不是生产事实）：

> 第 7 集  ｜ 1080p · SDR → 4K · Dolby Vision  ｜ 等待115秒传
> 本轮目标：DDP；已失败2次，下次重试时间已知时显示剩余时间。
> 当前可用操作：查看详情；仅在后端授权时显示换源/取消等动作。

限定：
- `miss_limit` 的总次数语义须核实，不能把“2/6”擅自解释为剩余6次。
- 只有可靠的 current_quality 才能作为版本摘要；没有实测播放证据不标“可播放”。
- 候选规格标注“发布者标注”，实际核验字段标注相应来源；不改变证据等级。
- 多视频、多字幕、多版本、跨集共享资产必须保留展开入口，不将它们拼成不存在的单一版本。
- 相对时间由服务器 due 计算，只是显示。演练/暂停/未知结果时明确不承诺执行；同时保留可查看的绝对时间。
- 无明确 next_at 时按具体阶段说明继续条件，不要所有阶段都显示“下一次检查时间尚未取得”。

不得在一集常态行重复“尚未确认入库”“本轮入库尚未确认”“已有记录继续单独展示”等多句等价免责声明。必要性应编码为状态、字段来源或详细说明。

候选比较：当前按集循环输出多条相同理由。对于同一候选、同一原因且范围明确的目标，可先汇总为范围/数量；展开再展示每集及每版本区别。列表摘要只覆盖部分目标时必须标注覆盖数，不能把8条推断为完整16条。不能把实际不同原因合并成统一结论。

## 4. 产品词汇表，而不是把内部枚举逐字翻译

技术词 SDR/HDR、Dolby Vision、DDP、PGS、STRM、RSSHub、CD2 可保留并提供首次解释；不得为了白话改变其意义。

| 内部/当前措辞 | 业务页面建议 | 必须守住的边界 |
|---|---|---|
| 目标/目标单元 | 第几集、电影正片、待升级版本 | 数量未知不能假装整季总数已知 |
| 基础音频档 | 普通音轨；能取得编码时显示实际编码 | 档位不能倒推出AAC等具体编码 |
| 本轮入库尚未确认 | 升级未完成，或具体等待步骤 | 历史库内版本与新版分别保留 |
| 发布/交付 | 上传到115、交给Symedia、等待Emby确认 | 按真实阶段使用，不能混成单一“已入库” |
| 纳管 | 接管已有订阅/交给subscriBetter管理 | 明示原生执行权变化，不变更权限 |
| 抢占 | 下载中允许改换更好版本 | 取代/取消/清理规则不变 |
| 冷却 | 入库后多久再次检查升级 | 不重置后台独立计时 |
| 生命周期 | 自动升级期限/完结后的处理方式 | 不误停连载或缺集任务 |
| 私密保存+配置一致+本次响应 | 连接已配置·尚未测试/保存中/测试失败等组合状态 | 后台仍区分三阶段及部分成功 |

禁止无事实支持的“一切正常”“可播放”“已同步”。禁止用泛化的“需要核对依据”代替具体原因；确实不知道就说清缺少哪类信息。

## 5. 配置向导必须成为真正流程

现有 PlanSetup 的 go() 只切换步骤；最终 check() 才校验整份 Config。合法性最终有后端保护，不等于逐步配置体验完整。

要求：
1. 新建方案与编辑共享配置的上下文清楚区分，标题持续显示正在编辑的方案。
2. 每步有就近的必要字段说明、检查结果和可定位错误；允许后退，继续前处理依赖当前步骤的缺项。不要到最后才抛出跨组字段错误。
3. 一套底部主操作：中间步骤“继续”，末步“保存方案”。内部可顺序预检、保存、回读，但不要求用户手工点击三种事务按钮。
4. 不增加伪事务：部分成功明确保留相应进度，失败可从原上下文恢复；不得重发可能成功的外部请求。
5. 若仍使用全局配置保存接口，必须说明此次确实会提交哪些未保存改动；不得按钮写“仅保存当前方案”却保存其他组的草稿。
6. “另有7个方案使用”不是充分的影响预览：针对实际修改的共享对象和字段列出受影响方案。与本次改动无关的共享信息不要在所有步骤反复警告。不得自动复制共享对象或默默扩大修改范围。
7. 映射检查保留真实样本要求；首次无样本时给出同一流程内的恢复入口，不用手造ID。配置保存/路径转换核验/云端内容核验分别记录，用户看到的是清晰的待完成步骤，而不是未说明的技术分层。
8. 名称作为人类标签，稳定ID作为内部身份；改显示名称不应破坏关系。如果现有模型只能二者同一，则明确实现无损迁移或暂不提供重命名，不能伪装已支持。

AI连接流程也使用这个原则：填写、保存连接、明确测试。可以在一次用户操作后自动顺序执行多个内部阶段并显示进度，但新测试会发出请求并可能消费额度，必须明确，不能自动开启生产AI。端点敏感内容和密钥不在普通API或日志回显。共享权限与秘密存储预算继续受后端约束。

## 6. 具体反模式：不能再次交付

- 把五步向导做成旧对象表单的五个分页，四周还保留另一套相互争抢的导航/保存按钮。
- 点击进入详情之后，正文还提示“具体阶段见详情”。当前上下文应给出阶段。
- 每个字段缺失都重复一条醒目的未知说明，造成重要问题与无害缺省值同等显眼。
- 把权威后端的可靠性边界变成用户每次都要读的免责声明。
- 只增加标签、细线、折叠框，宣称形成了新的视觉层级。
- 用DOM未溢出、菜单可点击或测试数量证明设计好用。
- 为减少页面而删除计划保护，或为展示完整而伪造质量/进度。

## 7. 同次完整交付的设计与验收方式

不是再冻结这一版外观然后列零散修补项。先确定统一的视觉与交互方案，并用真实组件和代表性数据覆盖下列相互关联的场景；再完成全部页面接入与回归。保留已有数据层与业务功能。

必要画面：
- 订阅列表：活跃、暂停、停止、部分未知同时存在，不用14个历史测试任务代表所有使用体验。
- 剧集详情：至少6集混合状态，旧版和升级版并存，下载中、等秒传、等字幕、等Emby、未知外部结果都有清晰差别。
- 候选比較：同理由多集可以摘要，不同理由不能被掩盖；加载/错误/部分结果均明确。
- 全新方案：无任何预配置，从服务选择到可保存；中途错误、共享引用、刷新/返回后输入保护都要验证。
- 已有方案：一处修改明确影响，用户不用找另一组的引用。
- AI：未配置、已配置未测试、正在保存、部分成功、真实测试失败分别能够理解。

使用实际MP宿主主题，以1440×900、1280×720、390×844等参考尺寸检查常态、展开态、长中文、长路径和放大；具体尺寸是验收输入，不是硬编码布局。鼠标、键盘、滚动和返回都要实际操作；不同设备未测就如实记录。

固定三条产品验收：
- 在作品列表，不点击技术诊断就能辨认当前阶段以及哪一项需要处理。
- 在某集详情，不解析文件名、不阅读原始JSON就能说出新旧版本差别和未完成原因。
- 在首次配置，不查数据库、不手填内部ID、不跨页搬运回执就能完成一套方案。

以上主张是设计验收要求，不用任意“测试通过率”代替用户认可。不得向生产库注入测试任务；合成数据必须标注，视觉验证与真实业务链路验证分别报告。
